# Design: cyoda-go 0.8.3 support — scheduled-transition functions, `allowCycles`, strict schema version

**Date:** 2026-07-28
**Status:** Design — pending user review, then implementation plan
**Depends on:** cyoda-go **v0.8.3** (installed locally) — workflow schema **1.3**
**Packages:** `@cyoda/workflow-core` (major-class), `@cyoda/workflow-react`; downstream `cyoda-dev-console`

## Problem

cyoda-go v0.8.3 bumps the workflow-import contract from schema **1.2** to **1.3**. Three
things change for the editor, one of which breaks it outright today:

1. The workflow `version` tag is now **strictly validated** against a supported range
   (`[1.1, 1.3]`). `WorkflowEditor.tsx` hardcodes `version: "1.0"` for every new
   workflow, so **every workflow the editor creates is rejected by 0.8.3**.
2. `transitions[].schedule` gains a second, mutually exclusive timing mode:
   **`function`**, a per-entity callout that computes the firing time. This is a
   canonical-model change.
3. The import request gains **`allowCycles`**, which bypasses cycle detection — needed
   for the scheduled-polling pattern the release promotes.

Plus a set of newly-enforced 400s the editor currently lets through, and two of our own
constraints that are now *stricter than the server* and would reject valid files.

Independent review then surfaced a fourth, pre-existing break of the same severity:
**`startNewTxOnDispatch` is emitted in the wrong place**, so every workflow using a
`COMMIT_BEFORE_DISPATCH` processor is already rejected by 0.8.3, and the field is silently
dropped on the way in. See disagreement #3 below.

## Verification method

Everything below was confirmed against a **running 0.8.3 binary** (mock-auth instance on
`:18080`), per the runbook in `ai/cyoda-schema-versions.md` — not inferred from the
bundled docs. Where the docs and the binary disagree, the binary wins; **three** such
disagreements are called out inline (#1 `delayMs <= 0`, #2 `timeoutMs` lower bound,
#3 `startNewTxOnDispatch` position).

The design was then independently reviewed, with the reviewer re-running the claim
tables against the same binary. No claim failed to reproduce; the review's findings were
all omissions, and are folded in below.

> **Lesson recorded:** disagreement #3 was missed on the first pass because the field's
> position was checked against the OpenAPI document rather than against the wire. The
> OpenAPI is generated and can be wrong about placement. **Probe the binary, not the
> schema document,** for anything structural.

## Authoritative wire shape (schema 1.3)

```jsonc
{
  "importMode": "REPLACE",
  "allowCycles": true,                       // NEW: request-level, default false
  "workflows": [{
    "version": "1.3",                        // NEW: strictly validated, required
    "name": "wf", "initialState": "A", "active": true,
    "states": { "A": { "transitions": [
      { "name": "static", "next": "B", "manual": false,
        "schedule": { "delayMs": 86400000, "timeoutMs": 0 } },      // timeoutMs may be 0
      { "name": "perEntity", "next": "B", "manual": false,
        "schedule": {                                                // NEW: function mode
          "function": {
            "name": "compute-time",
            "resultKind": "Schedule",
            "calculationNodesTags": "sched",
            "attachEntity": true,
            "context": "ctx",
            "responseTimeoutMs": 5000
          }
        } }
    ] }, "B": { "transitions": [] } }
  }]
}
```

### `schedule` is an XOR — with a non-obvious presence predicate

Exactly one of `delayMs` / `function` is required whenever `schedule` is present, and
`schedule` is mutually exclusive with `manual: true`.

**cyoda-go's presence test for `delayMs` is `> 0`, not "key exists".** Anything `<= 0`
counts as *absent*. Confirmed:

| Payload | Server |
|---|---|
| `{"delayMs": 0}` | 400 — *exactly one of schedule.delayMs or schedule.function is required* |
| `{"delayMs": -5}` | 400 — same message |
| `{"delayMs": 0, "timeoutMs": 9}` | 400 — same message |
| `{"delayMs": -5, "function": {…}}` | **accepted** (counts as function-only) |
| `{}` / `{"timeoutMs": 500}` | 400 — same message |
| `{"delayMs": 100, "function": {…}}` | 400 — same message |
| `schedule: null` | **accepted** (treated as absent) |

> **Docs disagreement #1.** `cyoda help workflows` claims "Static mode: `delayMs <= 0`
> is rejected (`VALIDATION_FAILED`)" as a distinct rule. Empirically there is no such
> rule — `delayMs <= 0` is folded into the mode rule above. We therefore do **not** ship
> a separate `schedule-delay-not-positive` code; it would report an error cyoda-go never
> issues, with wording the user would never see in a 400.

### The `delayMs: 0` export leak

cyoda-go's **own export** emits `"delayMs": 0` alongside `function` (a Go zero-value with
no `omitempty`), and normalizes `attachEntity` to an explicit boolean:

```jsonc
"schedule": { "delayMs": 0, "timeoutMs": 500,
              "function": { "name": "c", "resultKind": "Schedule",
                            "calculationNodesTags": "s", "attachEntity": true } }
```

Re-importing that is accepted, because `delayMs: 0` reads as absent. Any parser that
treats the key as present will either reject its own server's export or re-serialize a
contradictory payload.

### `timeoutMs` has no enforced lower bound

`{"delayMs": 5, "timeoutMs": -1}` is **accepted**, despite the OpenAPI declaring
`minimum: 0`.

> **Docs disagreement #2.** Our current `TransitionScheduleSchema` uses `.positive()`,
> which rejects `timeoutMs: 0` — the *strictest legal setting* ("drop on any lateness").
> Tightening to `.nonnegative()` would still be stricter than the server and would fail
> to round-trip a file cyoda-go accepts. See §4.

### Schema `version` tag

Range check only — **not** feature-gated. A `schedule.function` workflow tagged `"1.1"`
imports successfully. Validation runs *before* model lookup, so a bad tag 400s even for a
nonexistent model.

| Tag | Result |
|---|---|
| absent / `""` | 400 *version is empty; required MAJOR.MINOR form* |
| `"1"`, `"1.0.0"` | 400 *not in MAJOR.MINOR form* |
| `"1.0"` | 400 *no longer accepted; minimum supported in major 1: 1.1* |
| `"1.1"` – `"1.3"` | accepted |
| `"1.4"` | 400 *too new; this server supports up to 1.3* |

**Export restamps the tag to `1.3`** regardless of what was imported. Discovery is at
`GET /help/workflows/schema-version/versions` → `{"current":"1.3","supported":[{"major":1,"minMinor":1,"maxMinor":3}]}`.

### `allowCycles`

`S1 →scheduled→ S2 →scheduled→ S1` is rejected without it (*infinite loop detected: A -> B
-> A via unguarded automated transitions*) and accepted with it. Unknown keys are still
hard-rejected at every level (`DisallowUnknownFields`), so the flag cannot simply be
tacked on for older servers.

### `startNewTxOnDispatch` lives inside `config` — we emit it in the wrong place today

> **Docs disagreement #3, and the most serious defect this design fixes.**

Both `cyoda help workflows` ("sibling field on the same processor object") and the
OpenAPI (`ExternalizedProcessorDefinitionDto.startNewTxOnDispatch`) place this field at
**processor** level. The binary rejects it there:

| Payload | Server |
|---|---|
| `{…, "startNewTxOnDispatch": true, "config": {…}}` (processor level) | 400 `BAD_REQUEST: unknown field "startNewTxOnDispatch"` |
| same, with `false`, any `executionMode` | 400 — same |
| `{…, "config": {…, "startNewTxOnDispatch": true}}` | **accepted** |
| `config` level, `true`, `executionMode: "SYNC"` | 400 `VALIDATION_FAILED: only valid with executionMode=COMMIT_BEFORE_DISPATCH` |

The server's own export confirms the position:
`"config":{"attachEntity":true,"calculationNodesTags":"t","startNewTxOnDispatch":true}`.

**The editor has it at processor level, and both directions are broken today:**

- **Serialize** — `normalize/output.ts` emits it at processor level and `PROCESSOR_FIELDS`
  allowlists it there, so **every workflow with a `COMMIT_BEFORE_DISPATCH` processor is
  hard-rejected by 0.8.3**.
- **Parse** — a real 0.8.3 export carrying `config.startNewTxOnDispatch` parses with zero
  errors *and zero warnings*, and the field is **silently dropped** (Zod strips unknown
  keys from the config intersection). Silent data loss on the library's core promise.

**Change:** move the field from `ExternalizedProcessor` into `ExternalizedProcessorConfig`
(`types/processor.ts`, `schema/processor.ts`), from `PROCESSOR_FIELDS` into
`PROCESSOR_CONFIG_FIELDS`, from `outputExternalizedProcessor` into
`outputExternalizedConfig`, and retarget the existing
`start-new-tx-without-commit-before-dispatch` rule in `validate/semantic.ts`.

**The `"0.7"` dialect is deliberately left unchanged** (decision recorded): 0.7 has no
strict allowlist, and no 0.7 binary is available to test against, so changing its output
would be an unverifiable guess.

### Newly-enforced 400s we currently allow through

| Payload | Server |
|---|---|
| `retryPolicy: "EXPONENTIAL"` | 400 *unknown retryPolicy (allowed: NONE, FIXED, or empty)* |
| `asyncResult: true` | 400 *not supported on this backend* |
| any `crossoverToAsyncMs` | 400 *not supported on this backend* |
| `schedule.function` with empty `name` or `calculationNodesTags` | 400 *requires name and calculationNodesTags* |
| `schedule.function.resultKind != "Schedule"` | 400 *must be "Schedule"* |
| `executionMode: ""` | accepted (defaults to `SYNC` at fire) |

## Decisions taken

| Axis | Decision |
|---|---|
| Dialect | **Extend `"0.8"` in place** — no new registry key, no `SUPPORTED_CYODA_VERSIONS` change, consistent with how 0.8.1 and 0.8.2 landed |
| Version tag | **Preserve existing, stamp latest for new** — round-trip an existing tag verbatim; brand-new workflows get the dialect's tag |
| Stale tag (`1.0`) | **Warning + an offered fix** — never blocks, never rewrites silently; the user applies the fix. Requires a new remediation seam on `ValidationIssue` (§4) |
| `startNewTxOnDispatch` in `"0.7"` | **Left unchanged** — no 0.7 binary to test against, so moving it there would be an unverifiable guess |
| Scope | **Core + validation + React UI** in one coordinated change |
| `asyncResult` / `crossoverToAsyncMs` | **Warning, not blocking** — rejected by cyoda-go but valid on Cyoda Cloud |
| `allowCycles` | **Round-trip the flag + add a cycle-detection rule** so the flag has in-editor meaning |

## 1. Canonical model — `@cyoda/workflow-core` (major-class → 0.x `minor`)

**`src/types/workflow.ts`:**

```ts
export interface ScheduleFunction {
  name: string;
  resultKind: "Schedule";
  calculationNodesTags: string;
  attachEntity?: boolean;
  context?: string;
  responseTimeoutMs?: number;
}

export interface TransitionSchedule {
  delayMs?: number;             // static mode; canonical only when > 0
  function?: ScheduleFunction;  // per-entity mode
  timeoutMs?: number;           // may be 0; may be negative (see §4)
}
```

**Flat shape, not a discriminated union.** The server validates this as "exactly one of",
and its own export emits `delayMs: 0` *next to* `function` — a union would need a lossy
pre-pass to even parse cyoda-go's output. The XOR is enforced by a Zod `.refine` plus a
semantic rule. `delayMs` becoming `number | undefined` still makes the compiler flag every
read site, which is the main benefit a union would have bought.

`timeoutMs` and `responseTimeoutMs` take **any integer**, not `.nonnegative()`. Both are
unbounded server-side (`timeoutMs: -1` and `function.responseTimeoutMs: -1` both accepted),
and the existing `FunctionConfigSchema.responseTimeoutMs` uses `.nonnegative()` — reusing
it wholesale for `ScheduleFunction` would walk straight into the too-strict trap §4
diagnoses for `timeoutMs`. `ScheduleFunction` therefore defines its own field rather than
reusing `FunctionConfigSchema`.

**`src/types/session.ts`:** `allowCycles?: boolean` on `WorkflowSession` and
`ImportPayload`.

**`src/schema/payload.ts`:** `allowCycles: z.boolean().optional()` on
`ImportPayloadSchema`. Easy to miss and load-bearing twice over — Zod strips unknown keys,
so without it the parser reads nothing, and `workflow-monaco` generates its JSON schema
from `ImportPayloadSchema`, so §5a's "picked up automatically" claim depends entirely on
this line.

**`src/types/processor.ts` + `src/schema/processor.ts`:** `startNewTxOnDispatch` moves off
`ExternalizedProcessor` and into `ExternalizedProcessorConfig` — see disagreement #3
above. This is a **fix to existing broken behaviour**, not a 0.8.3 addition.

## 2. Parse direction — `src/dialect/cyoda-0_8.ts`

`toCanonical` gains a schedule-normalization pass, composed after
`normalizeOperatorAlias` / `coerceCanonicalDefaults`:

- **Drop `delayMs` when `<= 0`.** Reproduces the server's presence predicate exactly; the
  export leak falls out as a special case rather than a one-off quirk. Non-lossy: no
  payload the server accepts as a static schedule is altered.
- **Drop `null` at `schedule` *and one level inside it*.** The server accepts all of
  `schedule: null`, `{"delayMs": null, "function": {…}}`, `{"function": null, "delayMs": 5}`
  and `{"delayMs": 5, "timeoutMs": null}` — every one currently fails our Zod parse with
  `schema-invalid_type`. Normalization must strip `null`-valued keys inside `schedule`,
  not just a `null` `schedule` itself.
- **Version tag preserved verbatim** — the server restamps on export anyway, so rewriting
  it would churn files the user didn't otherwise change.

`parse-import.ts` reads `allowCycles` off the payload (default `false`);
`parse-export.ts` defaults it to `false` alongside its existing `importMode: "MERGE"`.

The `"0.7"` dialect is unchanged and continues to omit the whole `schedule` subtree.

## 3. Serialize direction

**`src/normalize/output.ts`** — both ride the existing `OutputOptions.schedule` flag, so
no new option key and `"0.7"` output is untouched:

- `outputSchedule` emits `delayMs` only when defined, then `timeoutMs`, then `function`.
- New `outputScheduleFunction` emits in wire order, omitting absent optionals. We do
  **not** mirror the server's habit of defaulting `attachEntity` to an explicit `true` —
  absent means the same thing and omitting keeps output minimal.
- **`attachEntity: false` must survive.** The existing `outputExternalizedConfig` /
  `outputFunctionConfig` use `if (cfg.attachEntity === true)`, which *drops* an explicit
  `false`. §5 says function-mode reuses the processor-config field components; copying
  that emission pattern would flip the semantics (explicit `false` → absent → server
  default `true`). `outputScheduleFunction` must emit on `!== undefined`.

**`V0_8_WIRE_FIELDS`** — `schedule` gains `function`; a new `scheduleFunction` level is
added. Both are exported so the existing "no key outside these sets at any nesting level"
test covers the new nesting automatically.

**`src/serialize/payload.ts`** — `serializeImportPayload` emits `allowCycles` **only when
`true`**, so a document that doesn't use it stays byte-identical to today's output. Key
order is `importMode, allowCycles, workflows`: `prettyStringify` preserves insertion
order and the golden runner compares bytes, so the position is load-bearing, not
cosmetic.

**Version tag — `CyodaDialect` gains two fields.**

```ts
interface CyodaDialect {
  readonly version: CyodaSchemaVersion;   // existing: "0.8" — the registry key
  readonly schemaVersionTag: string;      // NEW, required: "1.3" — the in-document tag
  readonly acceptedSchemaVersions?: readonly {   // NEW, optional
    major: number; minMinor: number; maxMinor: number;
  }[];
  // …existing toCanonical / workflowsToWire
}
```

| Dialect | `schemaVersionTag` | `acceptedSchemaVersions` |
|---|---|---|
| `"0.7"` | `"1.0"` | absent — the 0.7 server does not validate the tag |
| `"0.8"` | `"1.3"` | `[{ major: 1, minMinor: 1, maxMinor: 3 }]` |

**Why on the dialect rather than a constant or a lookup table.** Both are version-specific
facts that are *not* tree transforms, and both are needed where no tree exists to
transform. `schemaVersionTag` is consumed by `defaultNewWorkflow` at workflow-*creation*
time — the workflow does not exist yet, so neither transform has run. `acceptedSchemaVersions`
is consumed by the semantic validator, and cannot be a `toCanonical` rewrite because we
deliberately preserve the tag rather than restamp it: the point is to *report* a stale
`"1.0"`, not silently fix it. A parallel lookup table keyed by version string would work
but can drift from the dialect registry — `registerDialect` is public API, so a
host-registered dialect would resolve via `getDialect()` and silently miss the table.

**`schemaVersionTag` is required, deliberately.** It breaks compilation for any
host-registered custom dialect, which is the correct signal: a dialect authored against
0.8.2 has no opinion about a strictly-validated tag, and its author should be made to
state one rather than inherit a wrong default. `acceptedSchemaVersions` stays optional
because "this server does not validate the tag" is a real state — it is exactly `"0.7"`.

**The array shape mirrors the server's discovery endpoint**, which returns
`supported: [{major, minMinor, maxMinor}]` — an array because multiple majors may be
accepted concurrently during a deprecation window. Mirroring it survives a future major-2
window without a shape change.

> **Naming hazard.** `ai/cyoda-schema-versions.md` warns that the two version axes must
> not be confused, and this change puts the second axis's data on the first axis's
> object: `dialect.version` is `"0.8"` (the cyoda-go dialect) while
> `dialect.schemaVersionTag` is `"1.3"` (the in-document tag). Both are `MAJOR.MINOR`
> strings meaning entirely different things. The interface needs a blunt doc comment
> saying so.
>
> Related but separate: `src/migrate/registry.ts` already owns the tag axis, keyed by
> `MigrationEntry { from, to }` tag values. These are **not** wired together — migrations
> transform documents *between* tag values; `schemaVersionTag` states which tag a fresh
> document gets.

`defaultNewWorkflow` in `WorkflowEditor.tsx` stops hardcoding `"1.0"` and takes the tag
from the active dialect. Existing workflows keep their tag.

## 4. Validation — `src/validate/semantic.ts`

**New blocking errors**, each mirroring a confirmed 400 and quoting the server's own
wording so the editor message matches what the user would otherwise see:

| Code | Fires when |
|---|---|
| `schedule-mode-required` | see below |
| `schedule-manual-conflict` | `schedule` present with `manual: true` |
| `schedule-function-incomplete` | `function.name` or `function.calculationNodesTags` empty |
| `unknown-retry-policy` | `retryPolicy` outside `NONE` / `FIXED` / `""` |
| `workflow-schema-version-malformed` | tag not in `MAJOR.MINOR` form, or major unsupported |
| `empty-state-code` | a `""` key in the `states` map |

**`schedule-mode-required`, stated precisely.** Evaluated on the canonical model *after*
normalization, so it never sees a `delayMs <= 0`:

> For each transition where `schedule` is present, count the modes present: `delayMs`,
> and `function`. If the count is not exactly 1, raise on that transition.

Zero modes covers `schedule: {}`, `{"timeoutMs": 500}`, and any `delayMs <= 0` that
normalization stripped. Two modes covers a genuine `delayMs > 0` alongside `function`.

### The version tag rule is split by severity, and carries a fix

The server distinguishes four failure modes, and they do not deserve the same treatment:

| Tag | Server | Editor |
|---|---|---|
| absent, `""`, `"1"`, `"1.0.0"` | *not in MAJOR.MINOR form* | **error** `workflow-schema-version-malformed` |
| `"2.0"` | *major version 2 unsupported; supported majors: [1]* | **error**, same code |
| `"1.4"` | *minor too new* | **error**, same code |
| `"1.0"` | *no longer accepted; minimum 1.1* | **warning** `workflow-schema-version-outdated`, **with a fix** |

Only the last case gets a warning. Rationale: a `1.0` file genuinely cannot be imported,
so the user must be told — but they have to *open* it in order to fix it, so the rule must
not block; and rewriting the tag silently would churn bytes they did not ask to change.
Hence: tell them, offer the fix, let them apply it.

Range-checked against the dialect's `acceptedSchemaVersions` rather than pinned to `1.3`,
because the `"0.8"` dialect spans 0.8.1 – 0.8.3 servers.

**This requires a new remediation seam.** `ValidationIssue` is today
`{severity, code, message, targetId?, detail?}` with no action field, and there is no
quick-fix prior art anywhere in the packages. This design adds an optional `fix?: { label:
string; apply(doc): doc }` (or an equivalent descriptor the host applies), plus UI in
`workflow-react` to render and invoke it. It is deliberately generic: `name-too-long`,
`annotations-too-large` and `null-criterion-not-last` are all candidates to carry fixes
later.

**Scope note.** `version: "1.0"` occurs 136 times across 71 files *in this repo* — but 63
of those are test/fixture files (mechanical sweep) and only 8 are shipped source: the
`defaultNewWorkflow` bug, five example workflow JSONs in `apps/docs-embed-demo`, and two
files referencing them. That count measures this repo's own test data and implies nothing
about how many real user files carry `"1.0"`, which is unmeasured. The five demo
workflows are real artifacts that fail against 0.8.3 and must be restamped.

Two consumption details. `validateSemantics(session, doc?)` takes the document
**optionally**, so `doc.meta.cyodaVersion` may be unavailable; the rule falls back to
`LATEST_CYODA_VERSION`, matching the convention already used in `serialize/payload.ts`.
This degrades safely — a 0.7-targeted document has no `acceptedSchemaVersions` once its
version *is* known, so the rule simply does not fire. And the rule adds a new dependency
edge `validate/` → `dialect/`; no cycle results, since `dialect/` imports from
`normalize/`, `parse/`, and `types/` but never from `validate/`.

`resultKind` is typed as the literal `"Schedule"`, so it needs no separate runtime rule —
but note an **absent** `resultKind` is also a 400, not just a wrong one, and Zod's literal
mismatch produces a generic message. Fold both cases into `schedule-function-incomplete`
so the editor's wording matches the server's.

### Adjacent defects in the same code paths

Neither is caused by 0.8.3, but §4 rewrites the rules directly on top of both, and both
are round-trip data loss — the library's core promise. Fixing them here is cheaper than
routing around them:

- **`outputExternalizedProcessor` fabricates an execution mode.** It emits
  `executionMode: p.executionMode ?? "ASYNC_NEW_TX"`, inventing a mode for processors that
  never had one — and inventing the *wrong* one, since the server's documented default is
  `SYNC`. It should omit the key when absent and let the server default apply.
- **`asyncResult: false` is dropped on round trip**, although 0.8.3 explicitly documents
  and round-trips the explicit-`false` case (only `true` is rejected).

**New warnings (non-blocking):**

| Code | Fires when |
|---|---|
| `async-result-unsupported` | `asyncResult: true` |
| `crossover-unsupported` | `crossoverToAsyncMs` set to any value |
| `schedule-timeout-negative` | `timeoutMs < 0` — behaves like `0` (drop on any lateness) |
| `unguarded-automated-cycle` | see below |

`async-result-unsupported` / `crossover-unsupported` **replace** the existing
`crossover-without-async-result` rule, which is inverted for this backend: it warns when
`crossoverToAsyncMs` is set *without* `asyncResult: true`, but cyoda-go rejects the field
unconditionally. Both are warnings rather than errors so users targeting Cyoda Cloud —
where the fields are honoured — are not blocked. Wording: *"rejected by cyoda-go;
supported on Cyoda Cloud only."*

`schedule-timeout-negative` is a warning, not a Zod constraint, precisely so the value
round-trips: the server accepts it, and rejecting it in the editor would corrupt a file
the user could import by hand.

**`unguarded-automated-cycle`** — a new cycle detector over transitions that are
`manual: false`, non-`disabled`, and criterion-less. Reported as an **error** when
`allowCycles` is false (the server rejects such an import), demoted to **info** when
true. This is the only genuinely new analysis in this change; it exists because the
scheduled-polling pattern 0.8.3 promotes is *by construction* such a cycle, so users will
hit it immediately.

**A scheduled transition counts as automated.** Confirmed: the `S1 →scheduled→ S2
→scheduled→ S1` payload — every transition carrying a `schedule` — is rejected as
*"infinite loop detected: A -> B -> A via unguarded automated transitions"*. The presence
of `schedule` does **not** exempt a transition from cycle detection, and the detector must
not treat it as one. Excluding scheduled transitions would make the rule miss the exact
case it exists for.

**Measured detector semantics** — the editor's rule must match all of these:

| Case | Server |
|---|---|
| self-loop `A →scheduled→ A` | **rejected** — self-loops count |
| explicit `criterion: null` on the edge | **rejected** — counts as unguarded |
| a criterion on *one* edge of the cycle | accepted — one guard suffices |
| `disabled: true` or `manual: true` on one edge | accepted — breaks the cycle |
| cycle inside an `active: false` workflow | **rejected** — inactive workflows are *not* skipped |

The `active: false` row is the trap: the rule must **not** skip inactive workflows, even
though workflow *selection* at runtime does. Detection is per-workflow rather than across
the merged stored set, so the editor's rule can be complete.

## 5. UI — `@cyoda/workflow-react`

**`src/inspector/TransitionForm.tsx`** — the schedule section gains a **Static delay /
Function** mode switch. Switching modes clears the other mode's fields. `timeoutMs` is
shared and stays visible in both (the server accepts it in function mode, though the
docs say a function schedule's expiry supersedes it). Function mode renders `name`,
`calculationNodesTags`, `attachEntity`, `context`, `responseTimeoutMs`, reusing the
existing processor-config field components.

Three existing defects in that form are in scope, since the rewrite lands on top of them:

- `TransitionForm.tsx:135` — typing a `timeoutMs` forces
  `delayMs: transition.schedule?.delayMs ?? 1`, silently inventing a 1 ms delay.
- `commitScheduleTimeout` guards `if (!Number.isInteger(parsed) || parsed <= 0) return;`
  — it silently refuses `timeoutMs: 0`, the exact value §4 argues must be expressible.
- `TransitionForm.tsx:359` — ticking the schedule checkbox writes `{ delayMs: 1 }`; this
  must become mode-aware.

Also update the notice at `TransitionForm.tsx:420` ("Firing a scheduled transition
currently returns 400 BAD_REQUEST") — see the stale-claims sweep in §5b.

**`allowCycles`** gets a toolbar toggle, since it now switches a validator rule on and
off. (`importMode` has no UI surface today; `allowCycles` warrants one because it changes
what the editor reports as an error.)

## 5a. Downstream packages — verified unaffected

The runbook requires a canonical-model change to be coordinated across all five
downstream packages. Checked: `TransitionSchedule`, `delayMs`, and `.schedule` appear
**only** in `workflow-react`'s `TransitionForm.tsx` (plus one comment in
`WorkflowEditor.tsx`). `workflow-graph`, `workflow-layout`, and `workflow-viewer` never
read the schedule subtree, so they need no change.

`workflow-monaco` needs no code change either — `schema.ts` generates its JSON schema
from `ImportPayloadSchema` at runtime via `z.toJSONSchema()`, so `function`, `allowCycles`
and the relaxed `timeoutMs` are picked up automatically.

**But the XOR is invisible to Monaco.** `z.toJSONSchema()` drops `.refine()` checks, so
in-editor autocomplete and squiggles will not flag a `schedule` with zero or two modes —
the semantic validator is the only guard for that rule. This is acceptable (the semantic
validator is what blocks a save) but must not be mistaken for coverage. A test asserts
`workflowJsonSchema()` still generates without throwing once the refine is added.

## 5b. Stale-claim sweep

0.8.3 **executes** scheduled transitions — the v0.8.0-era "schema/SPI placeholder, the
engine does not yet execute it" claim is now false wherever it appears:
`types/workflow.ts`, `schema/workflow.ts`, `dialect/cyoda-0_8.ts`, and the user-facing
notice in `TransitionForm.tsx`.

The accurate 0.8.3 statement is narrower: a scheduled transition **fires on its own**;
only firing it *manually by name* returns 400 `TRANSITION_NOT_FOUND` ("is scheduled and
fires automatically; it is not manually fireable"). Leaving the old wording in place
would actively mislead users away from a feature that now works.

## 6. Testing

**Golden fixtures are *derived from* real 0.8.3 exports, not raw copies of them.** The
golden runner asserts exact byte-identity *and* zero error-severity issues, which a raw
export can never satisfy — independently of anything in this design, exports serialise
transition-less states as `{}` and omit `disabled: false`, neither of which our serializer
reproduces. The existing fixtures are hand-normalized import payloads; the new ones follow
that convention. (An earlier draft of this section claimed raw exports drop in. They do
not, and never did.)

Byte-identical fixtures — captured from a real export, then normalized to the editor's
emission shape:

- static schedule (`delayMs` + `timeoutMs`)
- `timeoutMs: 0`
- function schedule, minimal
- function schedule with all optionals + `timeoutMs`
- cyclic scheduled workflow with `allowCycles: true`
- a `COMMIT_BEFORE_DISPATCH` processor with `config.startNewTxOnDispatch`

**Semantic-equivalence** regression tests (assert meaning, not bytes — these deliberately
do not round-trip byte-identically):

- the `delayMs: 0` export leak → parses as function-mode, re-emits without `delayMs`
- `schedule: null` and each `null`-valued inner key
- `attachEntity: false` survives a round trip
- a raw 0.8.3 export with `config.startNewTxOnDispatch` retains the field (today it is
  silently dropped — this is the regression test for disagreement #3)

**Fixture sweep.** Every existing fixture tagged `version: "1.0"` (63 test files) plus the
five demo workflows in `apps/docs-embed-demo` must be restamped, or the new
`workflow-schema-version-outdated` warning fires across the suite. One fixture uses
`"version": "1"`, which trips the malformed-form *error* and would fail the golden
runner's zero-errors assertion.

Semantic-rule tests assert each new code fires on the exact payload the server 400s on.
The live 0.8.3 instance on `:18080` is used to re-confirm each rule's trigger and the
message wording.

A byte-identity test asserts that a document using none of the new fields serializes to
the exact same 0.8 wire bytes as before this change.

## Known trade-off

Extending `"0.8"` in place means one dialect serves 0.8.1 through 0.8.3 servers. Two
distinct failure modes result, and the second is the one that bites:

1. **The version tag.** New workflows carry `"1.3"`, which a 0.8.1/0.8.2 server rejects as
   "too new". Existing tags are preserved, so this affects newly created workflows only,
   and the error message is self-explanatory.
2. **`DisallowUnknownFields`, which is far less forgiving.** Verified to bite at every
   level — top level, `schedule`, `schedule.function`, processor, and `config`. So
   `allowCycles: true`, or *any* `schedule.function`, sent to a 0.8.1/0.8.2 server fails
   with an opaque `400 BAD_REQUEST: json: unknown field "…"` — not a helpful
   version-mismatch message. A user on an older server who touches a new feature gets a
   JSON parse error naming a field they may never have typed.

Neither is mitigated by this design; both are the accepted cost of a single `"0.8"`
dialect. The alternative — a separate `"0.8.3"` dialect key — was considered and rejected:
it breaks the MAJOR.MINOR keying convention and requires a matching `cyodaGoVersion` entry
downstream for a distinction that only matters to users who have not upgraded.

## Out of scope

- Executing or simulating scheduled transitions in the editor. The `schedule` field
  remains configuration only.
- The `internalized` processor type — still reserved and rejected at dispatch; the
  canonical `ProcessorSchema` stays `externalized`-only.
- Modelling the `Schedule` function *result* shape (`fireAt` / `fireAfterMs` /
  `expireAt` / `expireAfterMs`). That is a compute-node contract, not workflow config.
